# Subscription-only Foundry

Foundry runs subscription-only by default. A fresh install, with no settings at all, runs the Claude Code worker and Foundry's decisions from the logins already on the machine:

- **Worker:** Claude Code, using the default Claude login (`~/.claude`, selected by leaving `CLAUDE_CONFIG_DIR` unset). Set `defaults.provider` to `codex` (for example with `defaults.model: "gpt-6.2-astra"`) to run main threads on Codex by default instead, on the Codex CLI's ChatGPT login (`~/.codex`). A project may set its own default (`projects[id].defaults.provider`), and any thread may start on another worker (below).
- **Decisions:** Claude Haiku 5.5 (`claude-haiku-5-5`) through the same Claude login (`~/.claude`), with every Warden of a project held warm in one Foundry-owned Claude Code process per project (the project Warden host, below). Wardens (advise, guard and review) use this decision profile; a thread's first name is its first message's words, with no decision call. Decisions run on the Claude login only, a Codex worker's Wardens included: the primed pool and Codex decisions were removed on 2026-11-21 (Aron: "tear that all off", R-2026-11-21-15).

No API provider is constructed in this mode. There is no paid fallback, no automatic retry and no model substitution. API-key providers need an explicit opt-in.

The worker and the decisions may share one login: both are shared holders of it, like the user's own concurrent CLI sessions. Gateways, Kingdom bindings and per-thread authentication selections cannot be mixed into subscription mode.


## Several logins of one runtime (Aron, 2026-11-02)

A runtime can have several subscription logins, for example three Claude subscriptions (inixiative, personal, work). Settings › Providers adds one: "Add a Claude login" runs `claude setup-token` (Anthropic's own sign-in: inference only, one year) on a terminal of its own in a fresh private home, `<foundry dir>/logins/<id>/` (0700). You finish it in the browser it opens, or paste the code the page shows back into Settings. The token is written only to `setup-token.json` (0600) in that home and handed to the native child as `CLAUDE_CODE_OAUTH_TOKEN` at launch; settings hold its path (`tokenFile`), never the token, and no response or log carries it. "Add a Codex login" runs `codex login` in a fresh `CODEX_HOME` the same way. The first login added keeps the machine's own login (`~/.claude`) in the pool, so a second subscription never drops the first; any login can be named or removed (a home Foundry made is deleted with its token; the machine's own login location is only forgotten). Code: `providers/login-setup.ts`.

Several logins of a runtime are balanced (`providers/login-pool.ts`): which one serves a launch is agent-session's `SubscriptionPool` ranking (`rankCandidates`) from each login's 5-hour and 7-day readings (`probeClaudeLimits` / `probeCodexLimits` in the login's own home, cached a few minutes, plus the `rate_limit` events its sessions report). An exhausted, rate-limited or cooling login is skipped, a login that fails its sign-in check (`claude auth status`) is set aside as needing signing in again, and when none can serve the launch is refused with each login's reason: there is never a fallback to an API key. A login that reports no usage windows (a `claude setup-token` login reports none) can't be ranked by usage, so the balanced routings then order by turns served in the last five hours. A thread keeps the login it last ran on while that login can serve, because its native session and prompt cache live in that login's home; it moves only when its login is exhausted, signed out or removed, or balancing is pinned to another login, and the move starts a fresh native session seeded from the thread's journal. Each move bumps the thread's binding epoch (`…:move:<n>`), so a thread that comes back to a login it left never resumes that login's older session. A login with a thread running on it can't be removed (409) until the thread stops. Every admitted turn records the login that served it (`<foundry dir>/state/login-runs.json`, `GET /api/providers/runs?thread=<id>`), which also lets a restarted daemon resume a thread on its own login.

`GET /api/providers/pools` reports each runtime's pool: the routing, whether it is balancing across how many logins or why it stopped (pinned to a login, one login, only one left, none left), each login's status (ready, signing in, needs signing in again, exhausted), meters and turns in the last five hours, and the last turns' logins. The rail's Status view shows it in its Subscriptions block with a scale per runtime; clicking the scale toggles the load balancer (balanced ↔ pinned to the preferred login), Foundry-wide; a project that sets its own `subscriptionPools` keeps its own and is named under the scale. Settings › Providers shows the same with the routing and preferred-login choices, and Analytics' capacity band reads the same record. A project on a Kingdom pool is balanced by Kingdom; its state is not shown yet (Kingdom FEAT-024).

Decisions (Wardens and the other decision roles) stay on the decision login (`subscriptionOnly.decisionSourceId`, default `~/.claude`); only main threads are pooled. Muse Code runs one login.

## Main threads

Main threads (the default worker and every enabled executor) run on models from five labs: Anthropic, OpenAI, Google, Meta and xAI (`MAIN_THREAD_LABS` in the core model registry). Other labs and gateways are refused as main threads in every mode. How each lab runs:

| Lab | Subscription (default) | With `apiTokens: true` |
|---|---|---|
| Anthropic | `claude-code` on the Claude login | also `anthropic` (`ANTHROPIC_API_KEY`) |
| OpenAI | `codex` on the Codex ChatGPT login | also `openai` (`OPENAI_API_KEY`) |
| Google | no harness yet (agent-session's ACP transport for Gemini CLI is a stub) | `gemini` (`GEMINI_API_KEY`) |
| Meta | `muse` (Muse Code, `muse serve`) on the user's own Muse login; off until Meta's subscription mode is turned on | `meta` (`MODEL_API_KEY`, Meta's pay-as-you-go Model API: separate billing) |
| xAI | no harness yet | `xai` (`XAI_API_KEY`) |

**Turns the Claude CLI starts itself** (`claude-wake`: a background shell or monitor the agent started wakes the session when it finishes) are full Foundry turns (`turns/native-turns.ts`, `TurnService.observeNativeTurn`): the thread shows Working, the turn is journalled and its final text is the latest answer, a message sent meanwhile queues behind it and a steer is refused with the reason, a restart pauses it like any running turn, and the Wardens are asked on it (guard, milestone, hand-back). Why: a wake that ran unseen left the thread reading as done while the agent worked, and a message sent then collided with it. A wake that starts while a Foundry turn runs goes live on its next event once the thread is free. The restart note lists the background commands that were still running, since a restart stops them. Muse's self-started turns stay observed only (below).

A refused main thread names what it needs, in the settings API, the viewer's Defaults editor and setup.

A Codex worker is checked with `codex login status` and must be a ChatGPT login; an API-key login is refused. It runs on its own Foundry-private `CODEX_HOME` (`.foundry/runtime-profiles/<source id>/codex-home`, kept across restarts so sessions resume) that links the profile's `auth.json`. None of the user's Codex config, instructions or MCP servers apply to it, and it runs with Codex's own sandbox and approvals off, like the Claude worker's bypass mode.

A Muse Code worker (FEAT-006) runs through agent-session's `MuseSession` on the user's own Muse login, referenced in place (`$XDG_CONFIG_HOME/muse`, by default `~/.config/muse`), or, in a Kingdom-capacity project, on a Muse login its pool releases (native-authentication.md, "Kingdom-held subscription logins"). No other local Muse profile is supported, because moving it means moving `XDG_CONFIG_HOME`, which every command Muse runs inherits; the Kingdom path moves it and links the user's other config in. Why it is a native worker and not an API provider: a Muse subscription is billed only through Meta's own CLI, while the `meta` provider's `MODEL_API_KEY` is pay-as-you-go.

- **The login is the proof.** It is checked with `muse usage --json` (no model turn): signed in when it reports an allowance tier; nothing else about the account is read. The CLI must be the version agent-session's SDK is pinned to (`MUSE_SDK_VERSION`, 1.4.20); the doctor reports a mismatch, and agent-session refuses a host serving another version.
- **Nothing competes with the login.** A Muse launch loses every inherited Meta key and endpoint (`META_*`, `LLM_*`, `MODEL_*`, `LLAMA_*`, `OPENROUTER_*`, `TBH_AUTH_BASE_URL`, `TBH_MINT_BASE_URL`) and Muse's switches for the model, experiments, contributor mode, the approval judge and a fail-open permission profile (`withoutCompetingCredentials`), and gets `MUSE_NO_AUTO_UPDATE=1`, so the CLI stays on the pinned version. In subscription mode it launches with the same environment allowlist as the other workers (`boundLaunchEnvironment`, plus `XDG_CONFIG_HOME` / `XDG_DATA_HOME` so it finds the user's login and sessions). Muse's own tool runs inherit that environment.
- **Access follows the host.** Full access (and no host mode) is `allowAll` with the `:unrestricted` profile and no sandbox; a gated mode is `promptUnmatched` with `:ask-me`, so every approval reaches Foundry's tool gate and approval queue, never Muse's AI reviewer. Like Codex, a thread with structural deny or prompt rules is refused at launch: Muse's only pre-use stage is a vendor hook.
- **Questions.** A question Muse asks (`userInput/request`) goes to the thread's person on the same `ActionQueue` the tool gate asks on (a `choice` prompt for a single choice, else `input`), so it shows as "the agent asks" and the viewer answers it. foundry-acp forwards only approvals, so a question asked under an ACP host waits for the viewer or its timeout. A rejection, a timeout (15 minutes) or nobody to ask cancels it with a reason, so the turn goes on.
- **Turns Muse starts itself** (cron firings, monitor and background-terminal wakes, goals, messages from its other clients) land on the thread as observed turns, journalled and pushed live (`turns/native-turns.ts`); their lifecycle also shows as a running task, and one still open when the session ends is closed as failed. The thread then reads as done (its last turn completed). An orange "new arrival" needs the attention tag (`meta.attention`, the attention board's data, not built yet).
- **Resume.** The Muse session id is the thread's binding; a restart resumes it, and a missing one (or an ephemeral host that died) starts a fresh session seeded from the journal.
- **Kingdom pool.** A Kingdom-capacity project runs Muse threads (and may default to Muse) on its pool, never on this machine's login; a pool with no Muse login is refused with Kingdom's reason. A login Meta rejects is confirmed with `muse usage` and reported to Kingdom (`reportCredentialRejected`).
- **Not yet:** Foundry's tools and a host's MCP servers (agent-session offers Muse no session MCP, so Muse threads carry neither the `foundry` tools nor the note that teaches them), and decisions (Muse runs main threads only).
- **Personal only.** Archive captures of a Muse thread carry `runtime: { provider: 'meta', accessPath: 'subscription' }`, which Archive's `alwaysPersonal` keeps out of every organization. Foundry claims no Muse session with Archive's collector (claims name Claude Code and Codex sessions only), so the collector's Muse source captures the native transcript too, also personal. Muse may run in any project.
- **The login is released when `muse serve` has exited**, not when the session object closes, so a relaunch (a host's mode or effort changed) never resumes the session while the old host still writes it.

## Each thread picks its worker

A project has a default worker; any thread may start on another worker the user has a login for (FEAT-007). The worker is stored on the thread record (`ThreadMeta.worker`), set when the thread is created and never changed silently. `worker` names the provider running the thread's main session: a subscription worker (`claude-code`, `codex`, `muse`) in subscription mode, the default API provider (for example `anthropic`) with `apiTokens: true`.

- **Startup builds every offered worker.** A worker is offered when its vendor's subscription mode is on (or a project defaults to it), and each gets its own adapter, started on its own default model (the global model on the global worker). Building one spawns nothing: processes start per thread. A worker runs a local thread only with its login here: every default worker of threads run on this machine must have one, or Foundry refuses to start; another worker without one is simply not offered for local threads.
- **Choosing one.** `POST /api/threads` takes `worker`; the ACP agent reads `_meta.foundry.worker` on `session/new`. The worker can change whenever the thread is idle (`PATCH /api/threads/:id` with `worker`, or the ACP `worker` config option); while a turn runs or waits, the answer is 409. The launch view (`GET /api/threads/:id/launch`) returns the thread's `worker`, its models and `options.workers`. The viewer's command palette offers "New <worker> thread in this scope" for each other usable worker, and a thread's row tag names its worker.
- **Refusals.** A thread is refused (400 with the reason) when its worker is not a subscription worker, its vendor's subscription mode is off, or it has no login (`threadWorkerRequirement`, checked on create, restore and reopen). There is never a fallback to another login or an API provider. With `apiTokens: true`, every thread runs on the default provider.
- **What a thread on another worker runs.** Its view (`resolveThreadView`) is its project's view with the worker's default model (`SUBSCRIPTION_WORKER_MODELS`: `fable` for Claude Code, `gpt-6.2-astra` for Codex, `muse-wonder-1.0` for Muse Code) and its executors on that worker. An executor model pinned in settings that the worker does not run gives way to the worker's default; the launch view lists it under `setAside`.
- **Kingdom capacity.** A Kingdom-capacity project runs every worker on its pool, so its threads need no login here, and its default worker needs none at startup. A thread whose pool has no login for its worker is refused with Kingdom's reason and is never run on this machine's login.
- **Records.** Every thread record names its worker. At startup, before anything reads them, records without one are stamped once (`LocalSessionStore.stampWorkers`): from the runtime bucket of `.foundry/sessions.json` that holds the thread's own native binding; an observed subagent from its parent; a thread that never ran natively from its project's default, since no native session can disagree. A record bound under two runtimes, or one no worker owns, is left unstamped: it is retained on disk with a warning, a save never stamps it, and a main thread in that state stops startup. So a plain merge deploys. The main thread keeps the worker it last ran on. Observed subagents and forks carry their parent's worker.
- **Changing it.** A worker change before the first turn rebuilds the thread at once, with no await between the check and the rebuild.
- **Switching mid-conversation (Aron, 2026-11-02).** After the first turn a change carries the conversation over, not the old session's state. The route settles or refuses a lost turn first (`nativeRecovery`) and reads the session the thread held on the old worker; then, with no await between the last lock check and the save, it rebuilds the thread, journals a `worker-switch` row (from, to, that session kept on record) and saves the new worker. The store accepts a worker change after the first turn only behind that row. Only then is the old worker's session retired (`SessionBackedProvider.retireThread`, on `_forget`: ended, binding forgotten), so returning to a worker never resumes its stale session. The next turn starts a fresh session on the new worker, seeded once by `turns/journal-history.ts` (the CORE-004 seeding that fresh and forked sessions use): the conversation verbatim within `workerHistoryBudget(worker)` (a tenth of the worker's smallest context window, oldest left out past it), a "Continued on <worker> from here" marker, and the thread's plan. Foundry writes no summary of its own: what outgrows the window later is the harness's auto-compaction's (Foundry's rule against a separate summariser). The launch view lists `switches`, which the transcript shows as markers. A thread that ever ran on Muse stays personal in Archive (`runtime: meta`) after it moves off.

## Each thread holds its model; retired models move

The thread record holds the exact model it runs on (`ThreadMeta.model`: `{ id, alias? }`), and it is the only source: the native launch (`ThreadLaunchSettings.modelOf`), an API-mode executor on the thread's own worker (`ExecuteMeta.model` carries `{ id, worker }`; it replaces the agent's configured model only when the executor's provider is that worker, so an executor on another provider keeps its own), the launch view and the ACP agent all read it, and a change to a default applies to new threads only. Why: a thread whose model came from settings changed silently whenever settings or a CLI alias did, which is the silent change FEAT-007 forbids for the worker.

- **Aliases are pinned.** A thread created from `opus` (or a default naming it) stores the id the alias points to now (`claude-opus-5-5`) with the alias beside it (`defaultThreadModel`, `agents/thread-factory.ts`). The pickers offer only real ids (`choosableThreadModels`: no aliases, nothing retired).
- **One writer.** After creation only `changeThreadModel` (`turns/thread-model.ts`) changes it: a person's choice (`PATCH /api/threads/:id/launch`, refused while a turn runs or waits), a revival's answer, or succession. After the first turn it writes a "Switched to <model> from here" marker first (a `worker-switch` row with `from === to`, which is not a seed boundary), and the store refuses a model change after the first turn without one. It bumps the launch revision, so the warm session relaunches on the new model, resuming the same native binding. A worker switch writes one marker naming both changes ("Continued on <worker> with <model> from here").
- **Retired models (Aron, 2026-11-15).** The registry marks a model `retired: { at, successor? }` and keeps the entry; `readModelRetirement` follows the successor chain within the family on the same provider. Only open threads move, to the newest model of their family on their own worker; the worker never changes; a newer release never moves a model that is still served (`models/model-succession.ts`):
  - At boot, every setting naming a retired model (any `model` or `…Model` key, read against the provider in scope: defaults, project defaults, `subscriptionOnly.model`, Warden stages, agents, schedules) moves to its successor in one settings update audited as `foundry:model-succession`, and each idle open thread moves behind a marker with cause `retired`. A committed `.foundry/project.json` is the repository's and is not rewritten.
  - At the front of a thread's queue, before its turn starts, a thread still on a retired model moves the same way; with no successor the turn is refused with the reason.
  - A thread revived from archive on a retired model asks its person instead: a structural choice prompt (successor first) that holds every turn, a member's post included, until answered; a stop withdraws it and refuses the turn. The ask is held on the record (`ThreadMeta.retiredModelChoice`), so it survives a restart and the boot sweep leaves that thread alone.
  - A CLI that says the model does not exist (agent-session's `NativeModelMissingError`, read with `nativeModelMissing`) is retirement the registry has not caught up with. The failed turn moves the thread, behind the same marker, to the newest model of its family on its worker that is newer than it, and its error says so and asks to send again; with none newer it asks the person to choose a model and nothing moves (`ModelSuccession.modelMissing`, from the turn's failure in `TurnService`). Only the thread's own model counts: a missing model reported for another executor, a cancelled turn, or a failure in the move itself leaves the thread and its error as they were. Why: never down a family, and a plan limit or any other failure is not retirement, so only that error moves anything.

## Existing settings

Subscription mode sets the decision defaults (`defaults.decisionProvider`, `defaults.decisionModel`) to the decision profile. The saved settings file is not rewritten. Settings that cannot be enforced are refused: a worker that is not a subscription harness, an executor on another provider, a main-thread model the worker does not run, and `learning.review` provider/model overrides.

The default model is only the default. An executor (`agents[id].model`), a project (`projects[id].defaults.model`) and a thread (the launch settings a host or the viewer chooses) may each run any model its subscription worker runs, as its registry entry lists them (`workerModelRequirement`); a model of another provider is refused. Decision roles are different: a role cannot choose its model. Every first-stage decision runs on its runtime's decision login host (its project Warden hosts), which launches with the decision model and refuses a call naming any other; a later classify stage on another model or effort (the default Layer 2, Sonnet 5.5 low) runs on that stage's own decision host, launched with the stage's model (its own per-project lane).

## Sharing the user's own logins

Foundry adds processes to the logins the user already uses interactively, like another terminal session would. It does not change their files or settings:

- **Profile locks.** Subscription workers and decisions are shared holders of their login: each registers `.foundry-auth-shared/<owner>.json` in the profile (`~/.claude` or `~/.codex`) for its lifetime, and the last holder removes the directory. Claude decisions hold one registration for the decision host's lifetime. An exclusive `.foundry-auth-lock` (a non-subscription native profile) and shared holders refuse each other. Every lock is released when its process exits, including on a clean shutdown, which stops live processes first. Interactive `claude` and `codex` sessions ignore these locks. After a hard crash, remove a lock only after confirming the recorded Foundry owner and its children are dead.
- **User settings.** The Claude worker launches with `--setting-sources ""`, so the user's hooks, permissions and plugins in `~/.claude/settings.json` do not apply to Foundry's worker. A project Warden host launches with `--setting-sources ""` too, and with no MCP server but its own, no slash commands and no CLAUDE.md (`PROJECT_HOST_ARGS`, `PROJECT_HOST_ENV`).
- **Credentials.** Child environments drop API keys and competing profile overrides (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `CLAUDE_CODE_*` credentials, inherited `CLAUDE_CONFIG_DIR` and `CODEX_HOME`). No credential is copied or moved.

## Decision login host

Every Warden call runs on the decision login host (`createDecisionLoginHost`, `providers/decision-login-host.ts`): it holds the Claude decision login, its used-up pause, the decision receipts and the launcher of every project Warden host, and serves Warden calls only; any other call is refused before anything is sent.

- **Login.** Before the first decision the host checks `claude auth status --json` for a `claude.ai` subscription login (never an API key) and registers as a shared holder; a failed check dispatches nothing. The CLI reports the served model (`claude-haiku-5-5` for Haiku 5.5), and a substitution is refused.
- **Working folder.** Every project Warden host of a decision login host runs in that host's own folder (`createDecisionLoginHost`, `providers/decision-login-host.ts`), `~/.foundry/hosts/host-<host id>/` (private, 0700, or the host refuses to start and says how to fix it; `decisionHostsDirectory`, which `FOUNDRY_HOSTS_DIR` moves and tests point at a temp folder): each project host in an empty `project-<hash>-<uuid>/` made for it at launch and removed when it stops or fails to launch. Nothing else is written there but Archive's run marker beside them, so a Warden finds no project files. The folder is outside every git work tree (R-2026-11-19-07, Aron: "Let's create a special directory for these to operate in, which we know is always empty"), because Claude Code runs its git snapshot (`status`, `log -n 5`, `rev-parse`, `config` …, 5–6 processes) at each session and subagent start: under `.foundry/decision-receipts` a project host ran it against Foundry's checkout for every Warden it started (152 git processes at once from one host, 2026-11-19). The folder and the hosts directory are stamped for Archive (`stampFoundryRun`), so their sessions are dropped as Foundry's own; the folder is removed when the host closes and is empty, and the hosts directory's stamp still covers anything a crash left. Receipts (`host.json`, `decisions.jsonl`) stay in `<receipt directory>/host-<host id>/`.

## Project Warden host

The Warden runtime since 2026-11-03 (Aron: "the Claude project is the only thing that actually makes sense"), and the only one since the primed pool was removed on 2026-11-21 (R-2026-11-21-15). Aron, 2026-11-02: "All of these wardens should always be warm… run and then output and then reset." Spec: Oracle `docs/foundry/PROJECT-WARDEN-HOST.md` (rev 2) and its review. Not yet measured: detection through the host against the stage-one bar (parked with the other tests). With project hosts:

- **One host per project.** One Foundry-owned Claude Code session per project with a chorus, on the decision login, built by the decision host (`createDecisionLoginHost`, `providers/decision-login-host.ts`, which also owns the decision login, its used-up pause and the receipts): an empty private directory in the host's working folder under `~/.foundry/hosts/`, outside any git work tree ("Working folder" above; Archive drops it). The launch is as bare as a subscription launch goes (`--bare` and `CLAUDE_CODE_SIMPLE` refuse subscription logins; Aron, 2026-11-02: "wardens should be as bare as possible"): `--setting-sources ""`, `persistSession: false`, `--effort` at the decision effort, `--strict-mcp-config` with only the host's own server, `--disable-slash-commands`, `--exclude-dynamic-system-prompt-sections`, CLAUDE.md off, no telemetry, non-essential traffic or autoupdate (`PROJECT_HOST_ARGS`, `PROJECT_HOST_ENV`). A `claude setup-token` decision login reaches it as `CLAUDE_CODE_OAUTH_TOKEN` through the login's own launch, so no keychain is read; the default `~/.claude` login is read by the CLI as usual. It is extended with agent-session's `ClaudeInSessionDecisions` (spec C's held, fresh-per-call members). It is never built through the session adapter, so main threads keep the user's harness settings.
- **Only while someone works in the project** (Aron, 2026-11-02: "only while you're working in a project would its wardens be turned on"). A project's host opens on the project's first activity after startup: a thread of it created or reopened after startup (`thread:added`, emitted once the thread's runtime is registered, so its project resolves; threads restored at startup are not work), a thread of it opened in the viewer (its `thread:<id>` stream), or a turn in it (`journal`, and the turn's own advice); `followProjectActivity`. It closes after `projectHost.idleMs` (3 hours since the project was last touched; Aron, 2026-11-19) without any. **A turn never waits for the host** (Aron: "wardens should try and inject in the delta of messages after their last injection. this fixes startup and the 20s window of resetting"). While the project's host is on its way (its roster being composed, starting, or retrying; `ProjectWardenHosts.serving` answers `starting`), and on a serving host for a Warden it holds no warm spare for (agent-session's `heldOnly`), a user message's advice to that Warden (the only held-only call, `CompletionOpts.heldOnly`) is refused unsent and recorded as `not-sent:not-held` with `catchesUp`: never started cold, and not shown as degraded (no Retry), since the next message carries it. A call the queue admitted for a host that is gone by the time it runs is refused the same way, never run outside the shared slots. Every other Warden call of a first stage (a guard, a review, a Retry, a subagent brief, a consumed item, a milestone, a hand-back) is refused unsent too while the host does not serve, `not-sent:not-held` without `catchesUp`, so it shows as a Warden that did not start, with Retry (Routing, below). A replacement starting beside a serving host does not count: the serving one keeps answering. The skipped Warden **catches up** on the thread's next user message (`WardenCatchUp`, `agents/warden-catch-up.ts`): each Warden's cursor is the last user message it answered, a chime or `NO_COMMENT` (a not-held skip, timeout or failure leaves it), and the next advice it is asked carries the user messages it missed since, oldest first, under "Messages since you last answered", before the current message (`AdviseOpts.earlier`, journalled as `earlier` on the participant). A Warden first asked at a message starts there, so one added mid-thread is not handed the history; a Retry on a user message that answers moves the cursor. The catch-up is capped at five messages with the current one, and at about 4k tokens (`CATCH_UP_MAX_MESSAGES`, `CATCH_UP_MAX_CHARS`); older misses are counted in one line, not sent. Only the user-message trigger catches up. The cursor is rebuilt from the thread's journalled advice rows when its runtime is restored, so a restart does not lose it; a failure to rebuild it is pushed as a warning and never quarantines the thread's learning. With no host serving at all (failed, closed, not yet opened) the user-message advice is skipped and catches up the same way. Opening a thread in the viewer counts as working in its project. Why: on 2026-11-11 a first turn after idle fanned 75 Wardens into the primed pool (16 at once) while the host set up (37 s): 16 answered, 16 timed out at Layer 1 and 43 expired in the queue, so the turn was nearly unadvised; the earlier fix (the turn waited for the host, up to the advise deadline) added that setup to the turn's latency and left the ~20 s of a reset unserved. Primed cannot serve a full chorus cold inside the Layer 1 share; the host, once serving, answers the whole chorus in a few seconds.
- **Roster.** On opening, on every settings change and every minute, an open host's roster is composed from a hidden thread of the project (`composeProjectRoster`, `agents/chorus-thread.ts`, the same hidden thread `chorus-advise` uses) and held (`ProjectWardenHosts.openProject`, `providers/project-warden-hosts.ts`). The refresh never opens a host. The same roster again changes nothing. A changed roster of the same size is held in place (spares holding the old text are retired as replacements hold). A larger roster starts a new host.
- **Stateless Wardens.** A held spare holds a Warden's system (charter, region instructions) and its stable prefix (the region's knowledge), nothing of any thread: the split is at `stablePrefix` with an empty standby. The thread's own part (its understanding, the thread state, the moment, the protocol) rides in the moment. Every thread of the project matches the same spares. Threads never pre-start or release the host.
- **Composition at the project root.** With project hosts a thread's Wardens compose at the project's path, worktree threads included (`projectWardenRoot`, `ThreadRuntimeDeps.wardenRoot`), so a worktree's unmerged role-file edit (`.foundry/roles/region/<region>/`) reaches Wardens once it merges. Wardens never get CLAUDE.md (Aron, 2026-11-02; no switch): a Warden is its charter, the project's warden brief (`.foundry/warden-brief.md`, the `warden-brief` ladder node) and its region, composed the same way for every thread and the host. Because Wardens bind to the project's registered path, every thread reads the registered checkout's warden brief and role files, not its worktree branch's; a brief edited on a branch reaches the Wardens once it is in the registered checkout. That is intended: one composition per project is what a shared host holds.
- **Run, output, reset.** Each held spare serves one decision and ends; its dispatcher starts its replacement at once. Every spare of a Warden starts from the same bytes (no token in its prompt: the host fills the member's token into its calls from who is calling; agent-session 0.20.0) and subagent caches are kept an hour, so a replacement reads the prompt the first spare wrote. Measured 2026-11-19 on this project's 32 Wardens: 96 replacements wrote 0 tokens and read about 25,000 each, where before each wrote about 22,800. The host process takes agent-session's chorus host charter as its system prompt, so the setup message is its stated job: without it a Haiku host declined to start its builders.
- **Routing.** Every Warden call of a thread (advice `<thread>:aux:domain:<d>`, guards, reviews `review:<g>:domain:<d>`, and later stages `domain:<d>:stage:<n>`) goes to its project's host while it serves (`projectHostTarget`, by `threadMeta(thread).projectId`, the login pool's lookup). A turn's advice takes none of the `maxConcurrent` slots; guards and reviews keep their class caps (3/4 and 1/2 of them) on the host too, so a burst of background reviews never holds up the next turn's advice. Held-only (the catch-up skip) binds a Warden's first stage only: a later stage escalates a yes already given, so it runs cold on its lane when no spare is held. A later stage whose lane does not serve is refused unsent (`not-held`) like any Warden call, and the Warden says nothing at that moment: classify `runStages` returns the run as not sent, so Layer 1's unconfirmed yes never reaches the thread (Aron, 2026-11-18: "when the layers are down, they just skip… they really should not be holding this process hostage"). A later stage that times out, fails or answers out of shape still leaves the earlier stage's outcome, as before. Advice and guard compose one system, so a guard uses the same held spares; a review holds no spare and runs as a cold member inside the host, never a process of its own. A later stage on another model or effort (the default Layer 2, Sonnet 5.5 low) goes to its own **lane**: a second host per project on that model (`ProjectWardenHosts.lane`, bound by that stage's decision host), opened and closed with the project's host, its roster the stage's Wardens (`composeProjectRoster` records each stage with its model), shown as its own line in the status strip. **No host serving, no Warden call** (Aron, 2026-11-18: "it should not be handling warden calls at all"; "I think it's a lot of resources for things that should be done kind of in call"). While a project's host does not serve (starting, retrying, failed, closed, or a thread without a project), every first-stage Warden call is refused unsent (`projectHostTarget` answers `not-serving`; `not-sent:not-held`): a user message's advice catches up on the next message (above); a guard, a review, a brief, a consumed item, a milestone, a hand-back or a Retry is not sent and is not caught up, shown as a Warden that did not start, with Retry. On a serving host, a Warden it holds no warm spare for is skipped the same way for user-message advice only. Host state changes are logged and failures pushed to the viewer's decision warnings. Why (Aron, 2026-11-18: "Those are not supposed to be separate processes. Those are supposed to be singletons"): on 2026-11-18 guards, reviews and Layer 2 still ran on primed sessions, one CLI per key with a cap that scaled with the roster (up to 106 regions); 161 of them starved the machine until the viewer's index took seconds, and killing them brought it to 1–5 ms. The pool is gone (2026-11-21, R-2026-11-21-15; chorus `docs/RETIRE-PRIMED-POOL.md`): a call that is not a Warden's has nowhere to go and is refused before anything is sent, and no daemon caller sends one. Cost note (inixiative-da, 2026-11-18): each spare on a host writes its charter and region prefix fresh, where a primed key reads it from cache, so the Sonnet lane can cost more per decision than primed Layer 2 did; a token-only spare prompt over a per-role agent definition would fix it and waits on Aron.
- **Subagents.** A main thread's subagent turns are guarded from the main thread's Wardens in every runtime and on every worker (on the host while it serves, like any guard), journalled on the subagent's node; nothing about them depends on the host.
- **Login.** The host runs on the decision login (`subscription.decision`), not on the thread's login or Kingdom pool.

**Bounds.** A used spare's replacement starts while it still answers, so the subagent bound is `roster × (spares + 2) × concurrentTurns + 2 + 2 × dispatchers` (a used spare's replacement, plus a guard or a review's cold member per concurrent turn; root and dispatchers), raised on top of the user's own cap (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`). `maxOrphans` is one dispatcher's members, `roster × (spares + 1)`. The setup deadline scales with the roster. One spare per Warden to start.

**Health and reset.** The host is Foundry's own process, so its whole state can be thrown away. Every 2 s the supervisor reads the host's process tree memory (`ps`) and whether it serves:

| Condition | Action |
|---|---|
| Process ended | Routing leaves it at once; a new host starts. |
| Not serving for two reads (orphaned out, root gone) | A new host starts (blue/green). |
| Memory over `maxRssMb` for three reads in a row | A new host starts while the old one serves; routing switches once it serves; the old one stops once its calls in flight settle. |
| Memory over `hardRssMb` on one read | Routing leaves it at once (its Wardens are skipped until the replacement serves), a new host starts, the old one stops once its calls settle. |
| More than `maxRecyclesPerHour` dispatcher recycles | A new host starts (blue/green). |
| A start fails (setup not serving by the deadline) | Retried after `restartBackoffMs`, doubling to 5 minutes; after `maxRestarts` failures in a row the host is failed and the project's Wardens are skipped; the minute's roster refresh starts it once more each minute while the project stays open. |

Why both memory bounds: a 15-round run of one process holding 75 Wardens (48 KB each, agent-session `scripts/measure-in-session.ts`, 2026-11-02) sat at about 1.0 to 1.4 GB between rounds, every fan-out peaked at 1.5 to 2.5 GB for about two seconds and fell back, and twice memory climbed at about 400 MB/s (to 5.9 GB, which fell back, and to 12.5 GB at the end, which did not). A single read over 1.5 GB is a normal fan-out; three in a row is growth; past 4 GB a replacement's ~30 s setup is too slow to wait for. Those readings were of the measuring script's whole process tree, the Bun parent included.

**Why (measured 2026-11-02, spec "Why").**

| | Primed (one CLI per Warden) | One process, 75 held Wardens |
|---|---|---|
| Processes, memory | 79, ~15 GB | 1, 650 MB idle → 1.9 GB after 4 rounds |
| Whole-chorus Layer 1, warm | 9–10 s (16 slots); 2 of 75 timed out in a live advise | 3.4–6.0 s per round, p95 call 5.6 s |
| Failures | — | 0 of 300 |

Queue position drove primed latency (2.5 s → 15 s); each Haiku CLI process takes about 35% of a core, so 75 processes need about 26 cores on a 10-core laptop.

**Refill.** A fan-out uses every spare; each dispatcher starts its slice's replacements at once, one Agent call each, and the dispatchers work in parallel. Measured 2026-11-19 with synthetic Wardens at machine load 240 to 365, two reloads each: every Warden held again 4.6 to 5.0 s after a message for 8 Wardens, 6.3 to 6.8 s for 32, 6.6 to 7.3 s for 48 and 11.7 to 12.4 s for 64 (slices of 8); 13 to 28 replacements started in the same second. The floor is two model turns in a row: a Warden's answer, then its replacement starting and reaching its hold. One dispatcher per Warden was no faster and set up slower (190 s against 43 s at 64), so the layout is `dispatcherCount`. A second message inside the reload finds some Wardens unheld: a user message's advice to those is skipped and catches up on the next (`not-sent:not-held`); a guard starts its own member on the host. Aron, 2026-11-19: "I'm really okay with 5 seconds. I wasn't okay with 20 seconds."

**Evals.** `scripts/evals/chorus-advise.ts` sets the host up as the daemon does and records it in `<out>/host.json`: setup, per message held (`warm`), own-member (`cold`) and unserved (skipped) counts with latencies, and memory every 2 s. `--message-file` may repeat (`--gap-ms` between, 0 back to back). `liveDecisionHosts(subscription, { project })` builds it. The charter eval over probes (`warden-charter.ts` and its report), which ran Wardens and their judges on the primed pool, is parked in Oracle `migration/foundry-pool-evals/`: until it is rebuilt on the project host, with the regions, the stage-one bar has no runner.

## Dev mode: a local Chorus host

R-2026-11-25-05 (Aron): in dev mode Foundry talks to a local Chorus host directly, no Kingdom. With `__chorus` set and dev mode on for a project (its own `__devMode`, else the machine's: `devModeOn`, `viewer/config.ts`), that project's Wardens, if its chorus is on, are Chorus's: no project Warden host is opened or held here (`holdProjectRoster` closes one that is open), and no Warden call goes through the decision login host or `createSubscriptionDecisions`. Turning it on or off takes effect on the next call.

- **Client.** One Chorus client on Signet's `chorus.*` contract (`createChorusRemote`, `providers/chorus-client.ts`): each call's input is parsed against Signet's schema before it is sent and its result after. The transport is swappable; the direct one (`directChorusTransport`, `providers/chorus-direct-transport.ts`) posts `{ projectId, input }` to `<url>/operations/<operation>` with `Authorization: Bearer <token>`, the token read on every call the way the API keys are (`providerKeyEnvironment`): the environment variable `tokenKey` names, else the keychain entry of that name held by `foundry`. A 400 is `invalid_request`, a 500 is Chorus's own `failed`, any other status (a 401, a 404) is rejected with it; a refusal Chorus answers with 200 (`chorus_warming`, `unknown_project` …) passes through; no token, a timeout (the call's deadline plus 5 s), a closed port or an unreadable answer is a transport failure. The project id sent is Foundry's own, so Chorus's `CHORUS_PROJECTS_JSON` must name the project by it.
- **One call per moment.** The orchestrator asks each Warden as it always does, through `chorusMoment` (`agents/chorus-moment.ts`) instead of the Warden's own `advise` and `guard`: the first Warden asked sends one call for every Warden of the moment and the rest share its answer, each handed back its own result, so deadlines, catch-up, the journal (each Warden's request is the call exactly as sent), chimes, the guard report and the degraded strip are the local path's. A user message is `chorus.advise` (one call per distinct set of missed messages, since a call carries one), a subagent brief `chorus.brief`, a consumed item `chorus.consumed`, a milestone `chorus.milestone`, a hand-back `chorus.handBack`, and a guard `chorus.guard` for the Wardens its triggers gate, built once and sent only if some Warden's journal took it. A Retry sends only the chosen Wardens. Input limits are Signet's own schemas and constants.
- **Outcomes.** One table, the same for advice and guard:

  | Chorus answered | Warden outcome |
  | --- | --- |
  | `chorus_warming` (the host is still starting its project) | `not-sent:not-held` (a user message catches up on the next one) |
  | any other refusal (`chorus_unavailable`, `unknown_project`, `invalid_request` …) | `not-sent:not-admitted` |
  | no token, or the host unreachable or rejecting the call (401, 404) | `not-sent:not-admitted` |
  | no answer in time | `failed:timeout` |
  | an answer off the contract | `failed:invalid-response` |
  | a Warden `failed`, a stage of it timed out | `failed:timeout`, else `failed:provider-error` |
  | a Warden `not-sent` with `catchesUp` (no session held), or a guard's `skippedDomains` | `not-sent:not-held` (a user message catches up on the next one) |
  | a Warden `not-sent` otherwise | `not-sent:not-admitted` |
  | a Warden the answer does not name | `failed:provider-error` |
- **Review.** Not sent: Chorus's `chorus.review` handler is a stub (`threadKnowledgeUpdates: {}`), so a completed dispatch's review is recorded deferred, not sent, for every Warden, never as a no-comment. Remote review waits until Chorus's is real.
- **Status.** Opening a thread of a chorus-on project touches the host (`chorus.projectActivity`, `chorus-remotes.ts`); its answer is the project's line in the status strip, e.g. `foundry serving: 32/32 held, served by http://localhost:4901` (dev mode) or `served by kingdom:api.inixiative.com` (hosted). While dev mode is on for the machine or any project, Settings → Dev probes the Chorus host's `/readyz` and the Oracle host's `/healthz`, and says whether each token is held where Foundry may read it (the variable, or a `foundry` keychain entry).
- **Three ways a project's Wardens run.** Local: dev mode off for the project and no Kingdom Chorus grant, so its Wardens run on this machine's project Warden host. Dev: dev mode on for it, so they go to the local Chorus host over the direct transport (`directChorusTransport`). Hosted: dev mode off and the project has `kingdomProject` plus a held Kingdom Chorus grant (`kind: 'chorus'`), so `createKingdomChorusTransport` (`kingdom-chorus-transport.ts`) resolves the granted Chorus resource via cached `SignetClient.describe()` and executes `chorus.*` through Kingdom's `access/execute` relay. One Foundry may run projects across all three modes at once.

## Scheduling

One process-wide scheduler serves every thread's decisions, with up to `maxConcurrent` processes at once:

- **Priority.** Calls carry `CompletionOpts.priority`: pre-message decisions (Warden advice) run before post-action guards, which run before learning review, which runs before debug reasons (`DECISION_PRIORITY.debug`). Guards may hold at most three quarters of the slots, reviews half and debug reasons a quarter, and the caps nest: a call starts only while its class and every background class above it are under their caps, so reviews and debug reasons together never pass half. With two slots or more a turn waiting to start always finds one, and with three or more guards always keep at least a quarter (rounded down).
- **Fairness.** Within a priority, the thread served longest ago goes next, so one busy thread cannot starve another.
- **Shedding.** A full queue (per thread, then global) sheds its oldest lowest-priority wait to admit a more urgent call; only a call that cannot displace anything is refused. Shed guards report as unchecked, never as all-clear.
- **Rate limits.** A usage or rate limit fails that decision without retry, pauses new starts with exponential backoff (5 s to 60 s) and is logged and pushed to the viewer's event stream. It does not close admission. While the account reports usage blocked, the warm host refuses decisions before sending anything and re-reads limits at most once a minute.
- **Failures.** A refusal before any native write (expired deadline, revoked preflight or registration) leaves nothing owned and does not close admission. A turn the runtime settled (a native failure, or a deadline whose interrupt was acknowledged or whose process exit was observed) leaves nothing owned either and does not close admission. A violation, a substituted model or an unproven result still closes further admission.

## Latency

Every advisor has to be fast, so the pre-message phase is one concurrent round:

- Every domain assessment starts on the message's first decision dispatch, against the same frozen message, with no parallelism cap by default (`maxAdviseParallel`).
- The worker starts once the slowest of them answers.
- Composition stays deterministic: configured order, hash provenance, and the sealed plan are journalled before the worker starts.

Speed comes from how each decision runs:

- Each Warden's advice runs on a warm held spare in its project's host; a Warden with no spare held is skipped and catches up, never started cold on the critical path.

Every decision has a 60 s deadline (`DECISION_DEADLINE_MS`; a Warden's advice defaults to it too). It is a safety net, not the normal path. It was 10 s until 2026-11-01, when a 70-Warden chorus on 16 concurrent calls timed out on 11 of 70 Wardens in a live template replay: the deadline was cutting real answers, not catching hangs (Aron: "really extend the timeout limit, and then we can figure out how to make things faster"). On a timeout: a late answer is recorded as a timeout and the call is cancelled.

Claude Haiku 5.5 at low effort, measured live on 2026-10-11 through the primed host (eight roles at once on one Claude login): a warm decision takes 1.1–4.3 s (median about 1.7 s); a cold role (status check, priming and a first fork) takes 5–7 s. One warm decision alone takes about 1.1 s.

The earlier Codex budget (`providers/decision-budget.ts`), measured live with `bun scripts/measure-decisions.ts` (six Wardens, gpt-6-luna at low effort, a spare `VIEWER_PORT`):

| | Before (per-call `codex exec`, classify → route → advise) | After |
|---|---|---|
| Message to worker start (turns 30 s apart) | p50 18.2 s, p95 22.7 s | p50 6.5–7.2 s, p95 8.2–8.7 s (two runs) |
| One decision | p50 4.3 s, p95 6.5 s | p50 3.5–3.9 s, p95 5.5–7.4 s under the full fan-out |

The budget is 7.5 s p95 per decision and 9 s p95 from message to worker start. About one decision in six is hedged. No websocket-to-HTTPS fallback appeared in 165 warm-host decisions. Back-to-back messages (a request burst every few seconds) trip provider throttling; those turns ended at the decision deadline (then 10 s; 60 s since 2026-11-01) and are reported separately.

The floor is the decision model's own first-token latency: about 2.2 s for gpt-6-luna alone, and about 3.5 s under a nine-decision fan-out. A faster decision model or provider lowers it without structural changes.

## No Warden pre-filter

Every Warden is asked at every trigger point that reaches it, on the decision model (Claude Haiku). A local-model pre-filter that skipped a Warden on a confident "not my domain" was built, measured and switched off on 2026-10-15 (no local model cleared 80% recall at a skip rate worth its latency: Kev-4B added 4–4.6 s before any Warden could start, Kev-0.8B and ModernBERT barely beat chance; the measurements are in Oracle `docs/WARDEN-EXPERIMENTS.md`). It was removed with every local model provider (Ollama, vLLM) on 2026-11-19 (R-2026-11-19-04, Aron: "Get rid of all these local models. We're not using them anymore. We're on Haiku."), so `foundry-acp setup` downloads no model and the daemon serves none.

## Ownership and bounds

Decisions are bounded per call and per process. Guards retain their existing post-action semantics. The deadline includes queue, preflight and priming time; cleanup has its own bounded wait. Revocation or shutdown closes waiting admission and cancels active decisions: refused before dispatch, or interrupted with the interrupt's acknowledgment (or the process exit) as settlement. A worker authentication check with unknown exit likewise blocks further checks for that authentication instance.

Logical thread/generation/dispatch/review-job ownership is preserved while physical native session identities remain private. Inspection and release require the exact owner and admission ID. Learning cannot inspect accepted answer content until model, tool, ownership, receipt and process-release checks pass.

Decisions on a project host carry the same ownership evidence: one answer per decision, the served model checked, and the host's settled turn observed on settlement.

## Integration limits

Local profile references are not Kingdom capacity grants. A project execution contract must independently authorize worker and decision roles, purposes, model identities, aggregate budgets, deadlines and generation revocation. Startup makes no model calls unless `FOUNDRY_STARTUP_SELF_TEST=1` is set. With subscription decisions the self-test is not run: each project host's start proves the decision login (`claude auth status`, then its setup turn). With API-token decisions it makes one decision call.
