# Paseo — architecture map and feature inventory

Source: `~/code/paseo`, clone of github.com/getpaseo/paseo at `1939ee79e` (2026-10-11), version 0.11.2.
Method: code read, read-only. No installs, builds, tests or daemon. Docs and comments were treated as claims and checked against code; mismatches are called out. Paths are repo-relative. `server/…` = `packages/server/src/server/…`; `AM` = `server/agent/agent-manager.ts`. Anything not verified in code is labelled **(docs only)** or **(speculation)**.

Comparison frame: inixiative's Foundry / foundry-core / agent-session / Kingdom. Paseo maps roughly as: daemon ≈ agent-session + Foundry runtime; plugins/lifecycle hooks ≈ (a thin slice of) Foundry middleware; Hub ≈ a Kingdom-like hosted layer (but closed-source and trigger-focused); relay ≈ remote reach without Kingdom-style grants.

**Registry and adding a provider** — `agent/provider-registry.ts`. **Solid.**
- `buildProviderRegistry` (:906): built-ins from `PROVIDER_CLIENT_FACTORIES` (:185) → plugin providers (cannot shadow a built-in id) → derived providers (`addDerivedProviders` :801).
- Derived providers come from `~/.paseo/config.json` `agents.providers` (`protocol/src/provider-config.ts:51`): `extends` (6 built-ins or `acp`), label, `command` (replaces argv — the wrapper hook), `env`, `options`, `models`/`additionalModels`, `disallowedTools`, `paseoTools` policy, enabled, order. Recipes in `docs/custom-providers.md`: Z.AI/GLM and Qwen as `extends:"claude"` with `ANTHROPIC_BASE_URL`; Codex against OpenAI-compatible endpoints; multiple profiles of one provider.
- Every session/client is wrapped (`wrapSessionProvider` :438, `wrapClientProvider` :475) to re-stamp provider id and merge config.
- `docs/providers.md`: new providers should arrive as plugins, not built-ins. Code agrees.
- Exact MCP tool preapproval (`toolPolicy`) only on claude, codex, opencode; others throw `ToolPolicyUnsupportedError`.

**Subscription vs API auth.** **Solid.** Paseo drives the user's installed CLIs, so their own logins (Claude Max, ChatGPT, Copilot…) apply; Paseo stores no provider credentials. API keys/base URLs are opt-in through per-provider `env`. The only keys Paseo reads itself are OpenAI keys for speech (`server/config-environment.ts:61-67`). Env assembly (`agent/provider-launch-config.ts:238-253`, `createProviderEnv`): daemon `process.env` → provider `env` → launch-context env (`PASEO_AGENT_ID`, `PASEO_AGENT_CWD`, `before("agent.session_open")` edits). Only parent-Claude vars (`CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`, …) and Paseo runtime vars (`server/paseo-env.ts:4-34`) are stripped; **all other daemon env (including secrets) reaches every provider and plugin provider**.

**Usage sources** (`plugins/*-usage-source`, built-in): read the CLI's stored credential (e.g. Claude reads macOS Keychain "Claude Code-credentials") and poll vendor quota endpoints (`api.anthropic.com/api/oauth/usage`, `chatgpt.com/backend-api/wham/usage`, `api.github.com/copilot_internal/user`, Cursor, Grok, Kimi, MiniMax, OpenCode Go, Z.AI). **Solid** (but relies on undocumented vendor endpoints).

### B. Session and agent lifecycle

- **States** — `protocol/src/agent-lifecycle.ts:1-7`: `initializing | idle | running | error | closed`. `ManagedAgent` is a discriminated union (`AM:449-484`); `BUSY_STATUSES = {initializing, running}` (`AM:582`). Transitions come from provider stream events (`AM:4412` dispatch; `turn_started`→running :4685, `turn_completed`→idle :4569, `turn_failed`→error :4608, `turn_canceled`→idle :4649; close → closed :1768). Turn identity is a separate state machine with settle tokens so an old cancel can't settle a new turn (`agent/agent-run-state.ts`). All mutations serialize through per-agent `runLifecycleMutation` (`AM:2396`) and `runForegroundMutation` (`AM:2914`). **Solid.**
- **Create** — `createAgentInternal` (`AM:1277`). Creation is journaled by idempotency key in `server/creation/` (survives socket loss and daemon restart; a retry joins or reuses; an unconfirmed prompt delivery reports `agent_request_outcome_unknown` instead of resending). **Solid** — a notable design (see §5).
- **Resume** — persistence handle `{provider, sessionId, nativeHandle?, metadata?}` (`agent/agent-storage.ts:34-42`). Lazy: `ensureAgentLoaded` (`agent/agent-loading.ts:62`) resumes on first demand and always re-hydrates the timeline from provider history. - **Archive** — soft delete (`archivedAt`) in `archiveAgentUnlocked` (`AM:1828-1871`): snapshot → mark archived → close runtime → provider-native archive hook → drop in-memory timeline → cascade to children (`cascadeArchiveChildren` `AM:1877`; children in another workspace or open in a tab are detached instead). - **Crash detection** — graceful shutdown closes every agent with a timeout and writes `closed` snapshots (`bootstrap.ts:1814-1835`, `:1885`). ### C. Streaming and wire protocol

- **Server** — `websocket-server.ts:821` (`WebSocketServer` on `/ws`, `verifyClient` = origin + host checks). Raw handling `:2285-2390`: binary → `decodeBinaryFrame`; text → `JSON.parse` → runtime zod `WSInboundMessageSchema` (:2307); `ping`→`pong` with a 45s application lease (`websocket/physical-socket.ts:7`); `session` → `Session.handleMessage`. **Solid.**
- **Envelope** (`messages.ts:7527-7605`): inbound `ping | hello | recording_state | session{message}`; outbound `pong | session{message} | hello.rejected`. `hello` carries clientId, clientType (mobile/browser/cli/mcp/hub), protocolVersion (`WS_PROTOCOL_VERSION = 1`, effectively unused for gating), auth, appVersion, ~15 client capabilities. Reply is `status` with `server_info` and **~80 boolean `features` flags** — the real compatibility mechanism (`docs/protocol-compatibility.md`: gate once on a feature, no fallbacks, every shim tagged `COMPAT(name): … remove after <date>`).
- **Message surface** — 206 inbound and 224 outbound session message types (≈427 distinct `type` literals in `messages.ts`). Biggest domains: checkout/git/forge (~42), workspace (~40), agent (~39), plugin (24), project (19), hub (16), fs (15). New RPCs use dotted `domain.ns.verb.request/.response` (`docs/rpc-namespacing.md`), coexisting with legacy flat `*_request` names. Errors: `rpc_error`. **Solid** (partial migration of names).
- **Timeline model** — 9 item types: `user_message`, `assistant_message`, `reasoning`, `tool_call` (running/completed/failed/canceled), `todo`, `error`, `notification`, `compaction`, `plugin` (`messages.ts:667+`). Stream events: `thread_started`, `turn_started|completed|failed|canceled`, `timeline`, `permission_requested|resolved`, `attention_required` (+ usage/mode/model changes internally). `agent_stream` frames carry `{agentId, event, timestamp, seq, epoch}`. Store: `InMemoryAgentTimelineStore` (`agent/agent-timeline-store.ts:33`) with a random **epoch** per hydration and monotonically increasing seq; projection merges text/reasoning chunks and collapses each tool lifecycle into one row (`timeline-projection.ts`). Daemon owns canonical timestamps. **Solid.**
- **Snapshot / replay** — `fetch_agent_timeline_request` is authoritative; live frames are best-effort. Fetch takes `tail|before|after` with an `{epoch, seq}` cursor, default 200 rows (`agent-timeline-store.ts:96-130`); epoch mismatch or a gap returns `reset` + tail. Clients page `after` until `hasNewer:false`, exponential backoff 1s→30s (`app/src/timeline/viewed-timeline-sync.ts`). Because the epoch regenerates on every hydration, **every daemon restart is a full reset for clients**. Directory data (projects/workspaces/agents) uses separate per-entity sequences + bounded tombstones and returns snapshots on stale cursors (`server/directory-sync/`). Client caches rows in IndexedDB / expo-sqlite, LRU 32 MiB per host. **Solid** but intricate (`docs/timeline-sync.md`).
- **Subscriptions** — "owned subscriptions" (`features.ownedSubscriptions`): each subscription has a server ID tied to the physical socket that created it (`agent.timeline.set_subscription`, `session.events.set_subscription`, `subscription.release`, terminals, checkout diff, fs). Selective timeline delivery when `selectiveAgentTimeline`. **Solid**, with a legacy dual path in `client/src/compat/`.
- **Backpressure** — agent stream: 60ms leading+trailing coalescer (`agent/agent-stream-coalescer.ts:4`), tool output capped at 64 KiB per item (`AM:538`); app smooths "arrival lumps" at render (`docs/agent-stream-performance.md`). Terminals: 5ms coalescing, snapshot fallback when output > 256 KB and client buffer > 4 MiB (`terminal/terminal-restore.ts:17`). Hard per-socket cutoff `MAX_PHYSICAL_SOCKET_BUFFERED_BYTES = 64 MiB` (`websocket/physical-socket.ts:4`) — **`docs/architecture.md` says 8 MiB (stale)**. **Solid for terminals, minimal for agent stream.**
- **Binary frames** — `[opcode][slot][payload]`; terminal `Output 0x01, Input 0x02, Resize 0x03, Snapshot 0x04, Restore 0x05` (`protocol/src/binary-frames/terminal.ts:10-16`; docs list only four); file transfer `0x10-0x12`, 256 KiB chunks. Over the relay, binary is raw ciphertext when negotiated, else base64. **Solid.**
- **Schemas** — zod is the source of truth; server validates inbound with runtime zod; clients validate inbound with **zod-aot** generated validators (`protocol/src/validation/ws-outbound.ts`, `client/src/daemon-client.ts:6376`); schemas must be "pure" (no transform/catch/preprocess). Append-only rule: new fields optional, never narrow. New enum values gated per socket via `session.supports(CLIENT_CAPS.x)`. **Solid** (zod-aot pinned + patched, `docs/protocol-validation.md`).
- **Creation journal** — see B; reconnect re-subscribes to an operation key.

### F. Middleware / interception (exhaustive)

Per-turn interception requires owning the provider (plugin provider), wrapping the harness binary (`command` override), or using the harness's own hooks (Claude/Codex settings), which Paseo loads.

- **Credentials** — one daemon password (bcrypt cost 12, `server/auth.ts:6`; `daemon.auth.password`, `paseo daemon set-password`, or `PASEO_PASSWORD`), presented in `hello.auth`, legacy `paseo.bearer.<pw>` subprotocol, or HTTP Bearer (`auth.ts:80-115`). **No password ⇒ no auth** (`session-admission-auth.ts:18`). A per-run local credential (32 random bytes, `$PASEO_HOME/local-credential`, 0600, deleted on stop; `server/local-credential.ts`) gives same-user CLI/Desktop owner access. **Solid** for the single-user model.
- **Pairing** — ConnectionOffer v2 `{serverId, daemonPublicKeyB64, relay}` as `https://app.paseo.sh/#offer=…` QR (`pairing-offer.ts`, `connection-offer.ts`; `paseo daemon pair`). Relay off for new homes until pairing consent. **The relay path admits a client with no password as owner even when a password is set** (`session-admission-auth.ts:22-25`, `COMPAT(relayPasswordOptional)`), so the QR link is the whole credential over the relay. No per-device revocation: rotate keypair/password. **Partial.**
- **Agent → daemon auth** — `/mcp/agents` accepts the per-run token or the password, **and is open when no password is set** (`auth.ts:141-163`); caller identity is self-declared `?callerAgentId=`. Agents can also run `paseo` with the local credential → full owner. **Partial / weak.**
- **Hub authority** — opt-in `paseo hub connect`: one-time enrollment token, daemon generates a 32-byte relationship secret stored in plaintext in `$PASEO_HOME/hub-relationship.json` (private file) and sends only a SHA-256 verifier (`relationship-controller.ts:23, 314, 407`). New relationships have no permissions; `paseo hub permissions grant hub.execute` grants daemon-wide agent/workspace creation; Hub cannot manage its own grants; close code 4403 revokes. **Solid** (daemon side).
- **Network hardening** — Host allowlist against DNS rebinding (`hostnames.ts`; HTTP and WS upgrade `websocket-server.ts:892-911`); origin allowlist (`paseo://app`, localhost variants, configurable `cors.allowedOrigins`); MCP SDK's own rebinding protection disabled in favour of the app-level one (`bootstrap.ts:1488`); binds 127.0.0.1:6767 by default. **Solid.**
- **Relay encryption** — Curve25519 `box.before` + XSalsa20-Poly1305 (tweetnacl, `packages/relay/src/crypto.ts`), static daemon key (`daemon-keypair.json`, 0600), ephemeral client key per connection; no in-session replay counters (admitted in `SECURITY.md`). **Solid** crypto.

### H. Remote and multi-device

- **Connection types** (`app/src/types/host-connection.ts`): `directTcp` (LAN/Tailscale IP, optional TLS + password), `directSocket`, `directPipe`, `remoteSsh` (desktop/CLI only; system OpenSSH tunnel to remote 127.0.0.1:6767, `protocol/src/ssh-transport.ts`), `relay`. No built-in tunnel provider (no ngrok/Tailscale SDK). **Solid.**

Self-hosted relays supported (`daemon.relay.*`). **Solid crypto, relay server in flux.**
- **Multi-host app** — routes keyed by `serverId` (`app/src/app/h/[serverId]/…`), per-host settings, host badges/colors, cross-host usage, workspace labels resolved per host; plugin API `useHosts()` / `getPaseoClient(serverId)` (`plugin-examples/hosts`). **Solid.**

## 5. Notable design decisions and lessons

1. **One daemon, many thin clients, one protocol.** App, CLI, desktop, plugins, Hub and SDK all speak the same Session protocol (`packages/client`); plugins get the same `PaseoApi` over IPC. Contrast for us: Foundry/Kingdom split responsibilities across services; Paseo concentrates everything in one process.
2. **Feature flags over protocol versions.** `server_info.features` (~80 flags) + per-socket client capabilities, append-only schemas, "no fallback paths", and `COMPAT(name): remove after <date>` tags as a grep-able cleanup backlog (`docs/protocol-compatibility.md`; e.g. `websocket-server.ts:1855-1913`, `session-admission-auth.ts:22`). A disciplined answer to app/daemon version drift on mobile.
3. **Provider history is the transcript authority.** Paseo does not store transcripts (`AM:4173`, `bootstrap.ts:949-962`). Less storage and no divergence from the harness, but every restart is a client reset (new epoch), and anything not in the provider's file is lost. Relevant to Archive: Paseo is a reader of provider files, as Archive is.
4. **Live stream is best-effort; fetch is authoritative.** Epoch + seq cursors with paged-to-completion catch-up (`docs/timeline-sync.md`, `agent-timeline-store.ts:96-130`). Clean model for flaky mobile links.
5. **Idempotent creation and delivery journals.** Creation keys and message ids journaled in `creations/` and `agent-requests/`; an uncertain delivery reports "outcome unknown" rather than resending (`server/creation/`, `message-receipts/`, `docs/hub.md`). Directly relevant to Kingdom→Foundry dispatch.
6. **Wrap the user's own CLIs.** Claude via the Agent SDK pointed at the user's installed `claude` (`claude/agent.ts:1756`), Codex via `codex app-server`, everything else via ACP. Subscription logins work and Paseo never holds model credentials. Same stance as our subscription-only rule.
7. **Provider-neutral steering with fallback.** `steerActiveTurn` optional; manager falls back to interrupt+replace (`AM:2837`). Lifecycle mutations serialized per agent with settle tokens (`agent-run-state.ts`) to avoid cancel/turn races.
8. **Orchestration via push, not polling.** Children steer a `<paseo-system>` notification into the parent's turn (`agent-prompt.ts:467+`), the skill tells agents not to poll. Advisor/committee/handoff are just prompts on top of `create_agent`.
9. **Semantic permissions on every RPC, before principals exist.** The enforcement table (`operation-permissions.ts`) shipped first; principals/grants are still docs (`docs/permissions.md`). The reverse of Kingdom's approach (grant model first).
10. **Untrusted-source gating for PR worktrees** (`workspace-automation-gate.ts`) and Hub untrusted-trigger rules (`public-docs/hub/security.md`): explicit authority separation between classifier and worker steps.
11. **"Lean core, extend by plugin"** (`docs/product.md`): new providers should be plugins; the plugin API covers UI surfaces as well as server hooks. But the hooks are deliberately shallow (create/launch/observe).
12. **Docs as gotcha store.** `CLAUDE.md` rules: "Integrate, don't append", "One fact, one doc", "Don't document logic". Still, the docs drift (8 MiB vs 64 MiB, 4 vs 5 opcodes, 11 vs 12 hooks, permissions model).
13. **Heavily agent-authored.** Most recent commits come from `paseo-bot`/`paseo-ai`; 450k-line daemon with 5–8k-line files (`AM` 5.5k, `session.ts` 8.7k, `codex-app-server-agent.ts` 7.5k, `messages.ts` 7.6k). Moves very fast; also illustrates the "codebase is 3x the needed size" risk.

## 6. Weaknesses and gaps

- **No real middleware layer.** No pre-prompt hook, no synchronous tool gate, no mid-session context change, nothing for internal agents (§3F). The interception that exists is create-time or after-the-fact. This is the gap Foundry targets.
- **ACP providers drop the system prompt** (Copilot, Cursor, generic ACP and all 38 presets) — `daemon.appendSystemPrompt` silently doesn't apply to them.
- **Auth is single-principal.** Every client is owner; no scoped grants, presets, invitations or per-device revocation despite `docs/permissions.md`. No password ⇒ no auth. Relay clients admitted without the password (`COMPAT(relayPasswordOptional)`). Agent MCP endpoint trusts a self-declared `callerAgentId` and is open without a password. Any MCP-enabled agent can answer any other agent's permission request.
- **Plugins are unsandboxed owners** (forked Node with full access, owner session); client plugin code runs in the app's JS context.
- **Secrets pass through.** The whole daemon env reaches every provider and plugin provider; Hub secret stored plaintext; push notifications send plaintext previews of agent output and permission requests to Expo, contradicting "your code never leaves your machine".
- **No durable transcript, no audit log, no cost ledger.** Timelines are in memory and rebuilt from provider files; per-turn usage is not persisted; no record of who approved what beyond logs.
- **Crash recovery gaps.** No startup sweep of stale `running` records; only OpenCode helper processes tracked in the managed-process ledger; atomic writes without fsync.
- **Queueing is client-local.** Prompts typed while an agent runs are queued in one client's memory; not durable, not visible to other clients or the CLI.
- **No Paseo-owned checkpoints.** Rewind depends on the provider; only Claude rewinds files.
- **Retention absent.** Archived agents, receipts and schedule run history grow forever.
- **Key services outside the repo.** Production relay (Elixir/Fly) and the Hub trigger/workflow engine are not here, so the remote and automation stories can't be fully audited from source.
- **Docs drift** (backpressure limit, terminal opcodes, hook count, permission model, `create_workspace` bypassing the workspace hook).
- **Scale and bus factor.** One maintainer, very fast release cadence, many 5–8k-line modules, `paseo.json` parsing that silently discards malformed config (`.catch({})`).
- **Provider breadth vs depth.** Claude/Codex/OpenCode are deep; Pi/OMP/Copilot partial; Cursor/Kimi/Kiro/Trae/Antigravity and the ACP preset catalog are experimental (Antigravity runs with permissions bypassed).
